# Security Audit Report: Phase 1 — Payment & Licensing Threat Model

## Overview
This security audit evaluates the threat model across `POSgateway`, Firebase Cloud Functions (`functions/index.js`), and `SQLite_MifelaPOS` following Phase 1 hardening.

---

## 1. Razorpay Order Amount & Webhook Verification
- **finding:** **SEC-VAL-01 (Low / Informational)**
- **Observation:** `POSgateway` client submits order creation requests to backend. However, `POSgateway` creates the order server-side based on fixed SKU pricing or passes authorized amounts.
- **Webhook Validation:** `functions/index.js` `razorpayWebhook` strictly verifies the Razorpay signature via HMAC-SHA256 (`crypto.timingSafeEqual`) using `RAZORPAY_WEBHOOK_SECRET` stored in Firebase Secret Manager. It processes idempotency via Firestore transactions and records `paymentsByPaymentId` lookups.
- **Recommendation / Status:** Handled correctly. Ensure gateway server endpoints validate requested catalog pricing server-side before initiating Razorpay orders.

---

## 2. RSA-Signed Offline License Token Expiration & Re-Check
- **finding:** **SEC-VAL-02 (Medium / Tracked for Phase 2)**
- **Observation:** The RSA-signed offline license token generated by `verifyNodeLicense` (`functions/index.js`) includes `nextVerificationDue` (defaulting to 90 days).
- **Enforcement:** The client terminal stores the signed payload locally. If the terminal remains offline past `nextVerificationDue`, `LocalAuthService` / licensing state manager requires an online sync call to `verifyNodeLicense`.
- **Mitigation:** Firestore rules and `verifyNodeLicense` reject expired subscriptions (`subscriptionExpiry < now`) or revoked statuses (`status === 'REVOKED'`).
- **Recommendation / Status:** Active offline grace period is capped at 90 days; online re-verification is enforced upon expiry.

---

## 3. Firestore Rules Access Control
- **finding:** **SEC-VAL-03 (High / Immediate Action Recommended)**
- **Observation:** Direct client SDK access to Firestore collections (`payments`, `paymentsByPaymentId`, `provisioned_nodes`) must be strictly guarded.
- **Evaluation:** Clients should **never** have direct write access to `payments` or `provisioned_nodes`. All mutations to provisioning and payments must flow exclusively through Cloud Functions (`razorpayWebhook`, `verifyNodeLicense`, `resolveCustomerByDevice`).
- **Recommendation:** Ensure `firestore.rules` enforces:
  ```javascript
  rules_version = '2';
  service cloud.firestore {
    match /databases/{database}/documents {
      match /provisioned_nodes/{nodeId} {
        allow read: if request.auth != null || resource.data.fingerprint == request.auth.uid; // or server-only
        allow write: if false; // Only Cloud Functions (Admin SDK) can write
      }
      match /payments/{paymentId} {
        allow read, write: if false; // Admin SDK only
      }
      match /paymentsByPaymentId/{id} {
        allow read, write: if false; // Admin SDK only
      }
      match /razorpayWebhookEvents/{eventId} {
        allow read, write: if false; // Admin SDK only
      }
    }
  }
  ```

---

## Conclusion
Phase 1 security hardening successfully mitigates direct renderer tampering (CSP, batch write table/column restrictions, negative stock guards, structured DB errors, session-bound roles). Payment gateway webhook verification is cryptographically secured. Firestore direct client access should be locked down per `SEC-VAL-03`.
